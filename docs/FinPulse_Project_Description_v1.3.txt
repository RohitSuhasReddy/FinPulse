REVISION NOTES (v1.2 -> v1.3)
-----------------------------
This revision retains the original project's text-first, no-paid-LLM approach
and adds the core decisions made before development:
- Evidence-linked financial insights and news claims
- Structured financial metrics with units, periods, and source references
- Cross-source news comparison as a signature feature
- Explicit company, reporting-period, and publication-date context
- Modular, document-aware NLP pipelines instead of one rigid pipeline
- Testable output schemas, evaluation, error handling, and URL safety
- A more intentional graph-rendering and frontend architecture
- Frontend colors and visual palette deliberately left undecided; they will be
  chosen iteratively during UI design, not fixed in this document


1. PROJECT GOAL
---------------
Build a financial intelligence tool that helps a user understand a company's
latest earnings and the surrounding media coverage without manually reading
long transcripts or scattered news articles.

FinPulse will:
- Analyze earnings transcripts and press-release text using in-house NLP
- Accept one or more news article URLs, extracting and analyzing each source
  independently while preserving the source's identity
- Identify financial metrics and important management commentary
- Compare what different news sources emphasize, agree on, or appear to dispute
- Attach evidence (source sentences/passages) to important extracted claims
- Add basic historical stock price/volume context around an earnings event
- Present the results through a polished, readable, interactive dashboard

CORE PRODUCT IDEA:
'Earnings vs. Media Perspective' - what the company reported compared with
how different outlets discuss it.

FinPulse is an analysis and interpretation aid. It is NOT a stock-price
predictor, a trading signal, a fact-checking authority, or investment advice.


2. KEY PROBLEM THIS SOLVES
--------------------------
A. Fragmented financial information:
   Earnings releases, transcripts, and news reports are time-consuming to
   read and difficult to compare directly.

B. Different document formats:
   As learned from SpendSense (where bank statements had different PDF
   layouts), writing custom parsers for each company's earnings PDFs would
   become an unscalable maintenance problem.

C. Loss of source context in generic summaries:
   A single blended summary can hide which outlet reported a claim and which
   text supports a financial highlight.

FINPULSE'S RESPONSE:
- Treat cleaned earnings TEXT as the canonical input to the earnings pipeline
- Use generic PDF-to-text extraction only as a convenience fallback
- Analyze news articles separately before comparing them
- Produce evidence-linked, period-aware, structured results


3. INPUT STRATEGY AND MVP BOUNDARIES
------------------------------------
Primary earnings input:
- User pastes earnings transcript or press-release text
- For MVP, support one company and one reporting period per analysis

Optional earnings input:
- PDF upload with generic text extraction via PyMuPDF
- Clean repeated headers/footers, spacing, page numbers, and obvious noise
- Do not create company-specific parsers or promise robust table extraction
- Explain that text pasting is the more reliable path
- If extraction is poor, ask the user to paste clean text instead

News input:
- Up to THREE article URLs in the first complete MVP
- Extract article text, title, outlet, URL, and publication date when available
- Process each article independently before cross-source analysis
- Allow a paste-text fallback for inaccessible or paywalled articles, clearly
  identifying that the text was user-supplied

Context fields:
- Company name and ticker (user-selected or confirmed)
- Fiscal quarter / fiscal year, and earnings announcement date if known
- Article publication timestamps if available
- Do NOT silently merge different fiscal periods or unrelated companies

Demo scope:
- Prepare a polished, tested set of examples for 3-5 major companies
- Do not hardcode extraction behavior exclusively for those companies
- Permit additional companies through the same generic text-first pipeline


4. KEY FEATURES
---------------
MUST HAVE (across project milestones):

A. Earnings analysis
- Ingest and clean pasted earnings text
- Produce extractive highlights and concise key-point summaries
- Extract important financial metrics using rules + NLP features
- Analyze management commentary and financial sentiment at passage level
- Identify named entities and major themes
- Show supporting passages for material earnings insights

B. Structured financial metrics
- Capture, wherever present: metric name, value, unit/currency, reporting
  period, comparison basis, and cited source passage
- Examples: revenue, EPS, operating income, operating margin, guidance
- Distinguish percentage levels from percentage changes
- Distinguish YoY from QoQ, and reported from adjusted/non-GAAP values
- Never invent a value, a comparison, a confidence score, or a fiscal period
- If unavailable or ambiguous, mark the field 'not available' or 'needs review'

C. Per-source news analysis
- Show title/outlet/date/URL, short extractive summary, key claims, themes,
  and sentiment for each article
- Preserve which article each claim comes from
- Make key claims traceable to the article passage, where extraction permits
- Handle blocked, invalid, and unsupported links gracefully

D. Cross-source comparison ('Earnings vs. Media Perspective')
- Identify themes discussed in multiple sources
- Show where sources emphasize different risks, opportunities, or outcomes
- Flag possible differences or contradictions for user review, with evidence
- Compare company-reported points with the coverage surrounding them
- Do not claim that a source is true/false merely from similarity/sentiment
- Keep comparison text grounded in extractive source evidence

E. Stock context
- Show historical share-price and volume behavior around earnings
- Align the chart with announcement date and market session where known
- Mark the first appropriate post-announcement trading session
- Label missing timing information explicitly rather than assuming
- Do not imply that correlation proves earnings caused a price movement

F. Dashboard
- Clear progression: context -> earnings -> media -> comparison -> stock
- Financial metric cards with units and period labels
- Per-source news cards with links/evidence
- Cross-source themes and differences
- Clear graphs with legends, axes, tooltips, date ranges, and missing-data states
- Responsive layout, loading/error feedback, and a professional visual finish

GOOD TO HAVE (after core functionality):
- Export a structured analysis report (e.g., JSON/print-friendly)
- Optional dark/light modes
- PDF input fallback
- Additional article links / larger analyses
- Richer cross-source grouping after the simple baseline is validated

6. NLP DESIGN (IN-HOUSE; NO PAID LLM APIS)
----------------------------------------
Shared components:
1. Sentence splitting, text cleanup, and tokenization
2. Extractive summarization - start with TextRank
3. Key phrase and theme extraction - start with YAKE
4. Named entity recognition - spaCy
5. Finance-related passage sentiment - FinBERT
6. Evidence storage: originating source, selected sentence, and passage offset

Document-specific logic:

EARNINGS:
- Rules/patterns for financial metrics and units
- Fiscal-period and comparison-basis identification
- Management statements, risk comments, and guidance separation
- Distinguish transcript remarks from formally reported metric values

NEWS:
- Source metadata collection and outlet attribution
- Sentence/claim selection and article-specific summarization
- Source-level sentiment derived from passage-level signals
- Different article viewpoints stay separate

LONG-DOCUMENT HANDLING:
- Split long inputs into sentence-aware or token-bounded chunks before model
  inference, rather than feeding an entire transcript to FinBERT at once
- Store the relevant chunk/sentence for each produced insight
- Aggregate sentiment carefully; a numeric average is not the same as
  factual financial performance
- Expose ambiguous or low-evidence results as needing review

CROSS-SOURCE BASELINE:
- Start with simple normalized keywords / TF-IDF similarity and transparent
  grouping rules to match related themes across documents
- Add more complex embeddings only if the baseline proves inadequate
- Do not build a generative writing engine just to produce comparisons


7. EVIDENCE-LINKED DATA DESIGN
------------------------------
Important outputs should include a source reference, rather than only text.

For each EARNINGS METRIC, store approximately:
- metric_name, raw_value, normalized_value, unit, currency
- reporting_period, comparison_basis, metric_variant (reported/adjusted)
- source_id, supporting_text, location_in_source, extraction_status

For each NEWS CLAIM, store approximately:
- source_id, outlet, article_title, article_url, published_at
- claim_text, supporting_text, passage_location, theme, sentiment_label

For each ANALYSIS, store approximately:
- company_name, ticker, fiscal_period, announcement_date/time (if known)
- input types, processing status, warnings, results, analysis timestamp

A single normalized schema should feed both API responses and frontend charts.
Missing fields should be explicitly null/unknown, never filled with guesses.
SQLite stores reusable source metadata, fingerprints, cache entries, and
structured analyses; it is not just a text blob store.


8. ARTICLE EXTRACTION AND URL SAFETY
------------------------------------
Primary extractor: trafilatura; other extractors may be evaluated later.

Article processing steps:
1. Validate allowed URL scheme (HTTP/HTTPS), hostname, and resolved address
2. Reject local/private/reserved network destinations
3. Re-check redirect destinations and resolved addresses
4. Apply connection/read timeouts and response-size limits
5. Extract the article body and available metadata
6. Check for empty/boilerplate/low-quality extraction
7. On failure, show the affected URL and a readable reason; offer pasted text

Do not scrape through paywalls or promise every site will work. Preserve the
original URL and publication date when available. Treat retrieved page content
as untrusted input and never execute it in the dashboard.


9. STOCK CONTEXT
----------------
Source: yfinance for educational/research-oriented historical data.

Display:
- Price and volume in a defined window around a known earnings announcement
- An annotated earnings marker, with a before/after market indicator if known
- Price reaction for a clearly identified trading session and calculation
- Missing/no-data indicators if the stock or announcement timestamp is unclear

Avoid:
- Forecasts, trading strategies, or investment recommendations
- Hard claims that earnings directly caused a price change
- Using chart price movements as substitutes for reported financial metrics

Potential future extension (not MVP): structured company-filings data from
an official provider, where available, for financial-metric verification.


10. FRONTEND / UI / GRAPH RENDERING PLAN
---------------------------------------
Chosen direction: React + Tailwind CSS to allow fine-grained control over the
visual experience. Use clean reusable components for cards, charts, tables,
and expandable evidence passages.

IMPORTANT DESIGN DECISION:
The frontend COLOR PALETTE, accents, light/dark styling, and final visual theme
are NOT finalized yet. They will be chosen step by step during implementation
based on the owner's preferences. Do not lock in colors from mockups or early
examples. Use centralized theme tokens/CSS variables so future changes are easy.

UI flow:
1. Company and reporting-period header
2. Earnings summary and structured metrics
3. Per-source news cards
4. Earnings-vs-media comparison section
5. Stock reaction and volume charts
6. Source passages, warnings, and methodology details

Visualization requirements (regardless of final colors):
- Consistent reusable chart components, not one-off chart implementations
- Responsive rendering for desktop and smaller screens
- Hover tooltips with source, time, unit, and actual plotted values
- Readable axis labels, sensible ranges, fiscal/date formatting, clear legends
- Charts must distinguish factual values from sentiment/model outputs
- Label sentiment as model-estimated, not objective truth
- Support empty/loading/error/partial-data states
- Avoid excessive animation, clutter, or misleading scales
- Do not rely on colors alone to communicate positive/negative/mixed states;
  use text, icons, or patterns as needed
- Keep chart rendering independent from NLP logic and backend data access

Initial chart concepts:
- Price movement around an earnings date (line chart with earnings marker)
- Trading volume around that period (bars)
- Sentiment by news source (small comparison bars or other suitable plot)
- Financial metric cards and optional simple metric comparisons
- Shared themes / different emphases (cards/table first; chart only if useful)

Graph library: to be chosen during frontend implementation after testing the
required interactions and rendering quality (e.g., Recharts or Apache ECharts).
No finalized chart library or color palette is required to start backend work.

Design priority: trustworthy data display and polished interactions BEFORE
adding visual complexity simply for decoration.

Generic PDF extraction  : PyMuPDF (optional fallback)

Additional libraries should be introduced only when a measured requirement
justifies them. Respect model-weight licensing and third-party data-source
usage restrictions if the project is publicly distributed.


12. IMPLEMENTATION MILESTONES
-----------------------------
MILESTONE 1 - EARNINGS ANALYSIS ENGINE (START HERE)
- Establish project structure and typed/validated API result schemas
- Implement clean pasted-text earnings input
- Build text cleaning and NLP baseline
- Extract structured metrics and supporting passages
- Add passage-level sentiment and extractive summaries
- Create a small test corpus and evaluate extraction correctness
- Return stable JSON output even before building a frontend

MILESTONE 2 - MULTI-SOURCE INTELLIGENCE
- Validate and extract news article URLs with safe networking defaults
- Analyze each article independently, preserving outlet metadata
- Add grounded common-theme and difference detection
- Implement Earnings vs. Media Perspective
- Add SQLite caching and graceful source-level error handling
- Evaluate attribution accuracy and comparison quality

MILESTONE 3 - PRODUCT AND VISUALIZATION
- Build React frontend and reusable chart components
- Connect earnings, article, comparison, and stock-data responses
- Introduce graph tooltips, legends, interactions, and loading states
- Implement stock-session alignment and chart annotations
- Add best-effort PDF input and optional export
- Refine the color palette and rendering style collaboratively
- Prepare 3-5 polished demo examples

No requirement to implement every 'good to have' item before declaring the
first complete MVP usable.


13. TESTING AND EVALUATION
--------------------------
Evaluation is part of the core design, not a final cosmetic step.

Prepare representative examples of:
- Successful extraction from pasted earnings text
- Revenue/EPS/percentage identification and unit correctness
- YoY vs. QoQ, adjusted vs. reported, and different fiscal periods
- Long documents that require chunking
- News articles that discuss similar themes in different language
- A blocked/paywalled URL, an invalid URL, and an article with bad metadata
- Missing earnings dates / stock data
- Poor text extraction from a PDF

Assess:
- Correctness of extracted numerical metrics (against manually checked text)
- Correctness of source attribution and evidence passages
- Sentiment behavior on a manually labeled finance-text sample
- Summary relevance and preservation of key source details
- Whether comparison statements are actually supported by source passages
- API response stability and frontend error/empty-state handling

Document examples, strengths, limitations, and fixes for the portfolio.
Do not present made-up benchmark scores. Report measured outcomes only.


14. SCOPE CONTROL
-----------------
IN SCOPE:
- Single-company, single-quarter analysis workflow
- Text-first earnings analysis with source-linked highlights
- Optional generic PDF-to-text fallback
- Up to 3 news URLs in the initial full MVP
- Independent news analysis + cross-source comparison
- Local NLP models/rules, no paid LLM APIs
- Historical stock context around earnings
- React dashboard and useful, correctly rendered graphs
- Basic SQLite cache, testing, and clear error handling

OUT OF SCOPE (FOR NOW):
- Company-specific PDF parsers and perfect table reconstruction
- Automatic news discovery / continual crawling
- Investment advice or stock-price predictions
- Automatic judgments of source truthfulness
- Fine-tuning large NLP models
- Full coverage of every online publication or paywall
- User accounts, complex authentication, team collaboration
- Distributed infrastructure, large-scale deployment, and real-time trading
- Finalizing visual colors before frontend design discussions


15. SUCCESS CRITERIA
--------------------
A successful first complete FinPulse MVP should demonstrate that:
- The text-first earnings path gives usable outputs and understandable errors
- Material financial highlights retain source evidence and correct units/periods
- Missing or ambiguous metrics are not fabricated
- Each news source has a recognizable, independently attributable analysis
- Shared themes and differences are useful and grounded in the original text
- Historical stock charts are correctly labeled and session-aligned when known
- The UI is responsive, understandable, and visually consistent
- Graphs show data honestly with correct scales, dates, legends, and tooltips
- No paid LLM API is required for the core pipeline
- The project can be explained with concrete evaluation examples in interviews
- Adding a new company does not require new company-specific parsing logic


16. WHY THIS DESIGN IS STRONGER
------------------------------
- Keeps the practical lesson from SpendSense: avoid brittle document parsers
- Adds meaningful evidence and numerical correctness safeguards
- Moves beyond 'summarize 3 links' into explainable multi-source comparison
- Makes components testable and independently replaceable
- Leaves room for intentional frontend color and graph-rendering design
- Stays realistic for a student-built internship project


17. DECISIONS RESERVED FOR THE UI BUILD
---------------------------------------
These are intentionally open; do not assume defaults are final:
- Primary/background/accent colors and semantic positive/negative colors
- Overall light or dark appearance and theme variants
- Typography choices, spacing details, card shapes, and icon treatment
- Final visual graph styling, line weights, gradients, and animations
- Exact charting library after checking the interactive rendering requirements

We will make these decisions incrementally as the owner specifies preferences.
The data/API contracts and design tokens should support changes without
rewriting the application.
